# Coding Bible v0.28.0

v0.28.0 is the analyzer and remediation release. It expands deterministic
coverage substantially while keeping the project's central trust rule intact:
Coding Bible only automates conclusions that static evidence can defend.

## Highlights

- **77 of 128 Bible rules are automated.** The remaining rules are explicitly
  classified as 4 contextual candidates, 43 human / agent review rules, and 4
  external-tool responsibilities.
- **CSS and GraphQL are first-class analyzer languages** alongside JavaScript,
  JSX, TypeScript, and TSX.
- **Project-sensitive analysis is stronger**, including Next.js client/server
  import-graph checks and rename-aware changed-scope behavior.
- **Baseline lifecycle is complete** with `baseline create`, `baseline status`,
  and safe `baseline prune` semantics. Pruning removes stale fingerprints only;
  it never absorbs newly introduced debt.
- **Fix Pack v1 and Review Brief** provide deterministic remediation planning,
  safe/review patch separation, and prioritized review order.
- **Browser, CLI, GitHub Action, and MCP share the same analyzer contracts**,
  including self-describing custom-rule findings.
- **The GitHub Action is self-contained on Node 24** and carries its analyzer and
  TypeScript runtime under `packages/action/dist`.
- **MCP gains read-only `plan_fixes`** and keeps project/config/path access
  confined to its configured root.

## Automation boundary

The release intentionally stops at 77 automated rules. The four remaining
contextual candidates are not unfinished hard detectors:

- `APOLLO-001` needs schema/type-policy evidence to prove cache identity is
  actually missing.
- `APOLLO-004` needs mutation-result and cache-membership evidence to prove that
  normalized results cannot reconcile affected state.
- `GQL-006` needs schema/product evidence that a collection can grow without
  bound.
- `PERF-003` needs runtime or project-specific evidence that a collection path is
  both hot and large.

Promoting these from syntax alone would trade coverage numbers for false-positive
noise. The generated `docs/analyzer-automation-matrix.md` remains the source of
truth for the full 128-rule classification.

## Analyzer and CLI

- 77-rule automation policy with canonical DON'T/DO promotion contracts.
- Project-aware and source-file-aware detector dependency scopes.
- JavaScript/JSX/TypeScript/TSX/CSS/GraphQL source discovery.
- Baseline status and safe pruning.
- Versioned reports with self-describing built-in and custom findings.
- `--review-brief` for concise review ordering.
- `--fix-pack` for report, patches, prioritized plan, and Review Brief output.
- Cache and diff-scope hardening, including project-sensitive rules.

A clean run means clean for the **applicable automated subset**. It does not mean
all 128 Bible rules were reviewed automatically.

## Browser analyzer

- Persistent include/exclude rule selection.
- Local project analysis in a disposable Web Worker.
- CSS and GraphQL snippet/project analysis.
- Shared report and patch semantics with the analyzer package.
- Fix previews and separate safe/review patch exports.
- No artificial project file-count cap; large selections receive soft resource
  warnings instead.

## GitHub Action

- Source version: `0.28.0`.
- Changed or project scope.
- Baseline/config/rule-selection parity with the analyzer.
- GitHub annotations, Step Summary, SARIF, report, Fix Pack, Review Brief, and
  safe/review patch outputs.
- Self-contained committed runtime validated from a checkout with no workspace
  dependency install.

## MCP

- Source version: `0.28.0`.
- Read-only tools: `check_code`, `check_files`, `review_diff`, `plan_fixes`,
  `search_rules`, `get_rule`, and `get_project_guidance`.
- JavaScript, TypeScript, CSS, and GraphQL snippet analysis.
- Filesystem/config/custom-rulebook confinement to the configured root.
- Analyzer scans run without cache writes; `plan_fixes` does not modify source,
  cache, or baseline state.

## Custom-rule parity

Portable declarative custom rules remain intentionally narrow, but their finding
metadata is self-describing and survives the Web, CLI, GitHub Action, MCP,
report, and SARIF surfaces. Built-in rule IDs remain protected from collisions.

## Release checklist

Before creating the tag:

```bash
nvm use
pnpm install --frozen-lockfile
pnpm check:ci
pnpm release:tag:check -- v0.28.0
```

Then:

1. Promote the external Canary contract to the v0.28 denominator
   (**77 automated / 4 contextual / 43 human-review / 4 external-tool**) and
   confirm the full Canary suite is green against the exact candidate SHA. A
   green run against an older denominator is not a v0.28 release signal.
2. Confirm the repository **Quality gate**, **Self-contained Action smoke test**,
   and published-action dogfood jobs are green. The self-contained smoke must
   report non-zero `files-analyzed` and `rules-checked` outputs.
3. Tag that exact commit as `v0.28.0`. Release tags run the same quality/smoke
   workflow and verify that the tag matches the Action/MCP source version.
4. Create the GitHub release only after the tag workflow is green.
5. Smoke-test `Xanhast-pf/coding-bible@v0.28.0` from a separate repository.

After `v0.28.0` is actually published, update
`packages/action/release-state.json` and the immutable published-Action pin in
`.github/workflows/deploy-pages.yml` from `v0.27.0` to `v0.28.0`. Do this only
**after** the tag exists; source-development versioning and published dogfood are
intentionally decoupled.
